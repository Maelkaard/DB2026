# Занятие №12. Транзакции

## Что такое транзакция

Транзакция — это последовательность операций, которая выполняется как единое целое.  
Она переводит базу данных из одного согласованного состояния в другое согласованное состояние.

Пример: оформление заказа в интернет-магазине может включать такие операции:

- проверить наличие товара на складе;
- создать запись о заказе;
- уменьшить остаток товара;
- обновить сумму продаж менеджера;
- обновить сумму продаж филиала.

Если одна из операций завершится ошибкой, изменения нужно отменить, чтобы не оставить базу в некорректном состоянии.

## Свойства транзакций: ACID

Транзакции обычно описываются через набор свойств ACID.

### Atomicity — атомарность

Транзакция неделима: выполняются либо все входящие в неё операции, либо ни одна.

### Consistency — согласованность

После завершения транзакции база должна оставаться в корректном состоянии.

Это означает, что при выполнении транзакции должны соблюдаться все правила, заданные в базе данных:

- ограничения `NOT NULL`;
- ограничения `CHECK`;
- ограничения уникальности;
- внешние ключи;
- индексы;
- триггеры;
- другие механизмы контроля целостности.

### Isolation — изоляция

Параллельно выполняющиеся транзакции не должны некорректно влиять друг на друга.

Для этого используются уровни изоляции. Чем выше уровень изоляции, тем строже согласованность наблюдаемых данных, но тем меньше возможностей для параллельного выполнения.

### Durability — долговечность

Если транзакция успешно завершилась, её результат должен сохраниться даже в случае сбоя системы.

## Управление транзакциями в PostgreSQL

Для начала транзакции используется команда `BEGIN`.

Для завершения транзакции используются команды:

- `COMMIT` — зафиксировать изменения;
- `ROLLBACK` — отменить изменения.

```sql
BEGIN;

INSERT INTO ...;
UPDATE ...;
DELETE FROM ...;

COMMIT;
```

или

```sql
BEGIN;

INSERT INTO ...;
UPDATE ...;
DELETE FROM ...;

ROLLBACK;
```

### Точки сохранения

Внутри транзакции можно создать промежуточную точку возврата:

```sql
SAVEPOINT savepoint_name; -- создать
ROLLBACK TO SAVEPOINT savepoint_name; -- откатиться
RELEASE SAVEPOINT savepoint_name; -- удалить точку сохранения и все созданные позже нее
```

Это позволяет откатить не всю транзакцию целиком, а только её часть.

## Аномалии параллельного выполнения

При одновременной работе нескольких транзакций возможны различные проблемы.

### Грязное чтение (dirty read)

Транзакция читает данные, изменённые другой транзакцией, которая ещё не завершилась.  
Если вторая транзакция потом выполнит `ROLLBACK`, первая транзакция окажется прочитавшей данные, которых на самом деле никогда не было в каком-либо согласованном состоянии БД.

### Неповторяемое чтение (non-repeatable read)

Транзакция дважды читает одну и ту же строку и получает разные значения, потому что между чтениями другая транзакция успела изменить и зафиксировать данные.

### Фантомное чтение (phantom read)

Транзакция дважды выполняет один и тот же запрос по условию и получает разный набор строк, потому что другая транзакция добавила или удалила строки, подходящие под это условие.

## Уровни изоляции в PostgreSQL

Важно: PostgreSQL поддерживает не все уровни изоляции так, как они описаны в ANSI SQL.

В PostgreSQL доступны такие уровни:

- `READ COMMITTED`
- `REPEATABLE READ`
- `SERIALIZABLE`

Запись `READ UNCOMMITTED` допустима синтаксически, но в PostgreSQL она работает так же, как `READ COMMITTED`.  
То есть грязное чтение в PostgreSQL не допускается даже при указании `READ UNCOMMITTED`.

### READ COMMITTED

Это уровень по умолчанию в PostgreSQL.

Особенности:

- каждый оператор `SELECT` видит только данные, которые были зафиксированы к началу выполнения этого оператора;
- незафиксированные изменения, сделанные текущей транзакцией, видит только она сама;
- повторный `SELECT` в той же транзакции может вернуть другой результат, если параллельная транзакция успела зафиксировать изменения.

На этом уровне возможны:

- неповторяемое чтение;
- фантомное чтение.

Грязное чтение не допускается.

### REPEATABLE READ

В PostgreSQL этот уровень реализован через снимок данных _(snapshot)_ на момент начала транзакции.

Особенности:

- все `SELECT` внутри транзакции видят одну и ту же согласованную версию данных;
- изменения, зафиксированные другими транзакциями после начала вашей транзакции, не видны;
- при конфликтующих изменениях возможна ошибка при `COMMIT` или при попытке изменить строку.

На этом уровне в PostgreSQL не допускаются:

- грязное чтение;
- неповторяемое чтение;
- обычное фантомное чтение в смысле snapshot-чтения.

Но всё ещё возможны некоторые аномалии сериализации, поэтому существует уровень `SERIALIZABLE`.

### SERIALIZABLE

Самый строгий уровень изоляции в PostgreSQL.

PostgreSQL старается обеспечить такой результат, как если бы транзакции выполнялись строго последовательно, одна за другой.

Особенности:

- транзакция может завершиться ошибкой сериализации;
- в таком случае её нужно полностью повторить.

Типичная ошибка:

```sql
ERROR: could not serialize access due to read/write dependencies among transactions
```

## Установка уровня изоляции

Уровень изоляции можно задать при начале транзакции:

```sql
BEGIN ISOLATION LEVEL [READ COMMITTED | REPEATABLE READ | SERIALIZABLE];
```

Также можно посмотреть значение по умолчанию:

```sql
SHOW default_transaction_isolation;
```

## Особенности:

### Последовательности (`SEQUENCE`) не откатываются

Если в таблице используется `SERIAL` или `GENERATED ... AS IDENTITY`, то значение счётчика может увеличиться даже при `ROLLBACK`.

Это значит, что после отката транзакции могут появляться «пропуски» в значениях идентификаторов. Это нормальное поведение.

### Блокировки при изменении одной и той же строки

Если одна транзакция изменила строку, а вторая пытается изменить ту же строку, вторая обычно будет ждать завершения первой транзакции.

## Примеры

Для демонстрации работы транзакций потребуется подключиться к БД из двух разных консолей.

Создадим схему и таблицу:

**Консоль 1**

```sql
CREATE SCHEMA IF NOT EXISTS sem12;

DROP TABLE IF EXISTS sem12.test_table;

CREATE TABLE sem12.test_table (
    my_id SERIAL PRIMARY KEY,
    my_text_field TEXT
);
```

Начнем транзакцию в первой консоли:

**Консоль 1**

```sql
BEGIN; -- уровень изоляции по умолчанию

INSERT INTO sem12.test_table (my_text_field)
VALUES ('test_value1');

SELECT *
FROM sem12.test_table;
```

Транзакция видит собственные изменения.

Попытаемся обратиться к таблице из другой консоли:

**Консоль 2**

```sql
SELECT *
FROM sem12.test_table;
```

Во второй консоли строка ещё не видна, потому что транзакция еще не выполнила `COMMIT`.

Зафиксируем изменения:

**Консоль 1**

```sql
COMMIT;
```

Снова проверим таблицу из консоли 2:

**Консоль 2**

```sql
SELECT *
FROM sem12.test_table;
```

Теперь строка видна, потому что изменения были зафиксированы.

Начнем транзакции в обеих консолях:

**Консоль 1**

```sql
BEGIN;
```

**Консоль 2**

```sql
BEGIN;
```

Изменим строку из первой консоли:

**Консоль 1**

```sql
UPDATE sem12.test_table
SET my_text_field = 'updated_in_console_1'
WHERE my_id = 1;

SELECT *
FROM sem12.test_table;
```

Первая транзакция видит своё изменение.

Попробуем изменить ту же строку во второй транзакции:

**Консоль 2**

```sql
UPDATE sem12.test_table
SET my_text_field = 'updated_in_console_2'
WHERE my_id = 1;
```

Этот запрос не завершится сразу. Вторая транзакция будет ждать, потому что строка уже изменяется первой транзакцией.

Зафиксируем первую транзакцию:

**Консоль 1**

```sql
COMMIT;
```

После этого запрос во второй консоли будет выполнен.

Посмотрим результат:

**Консоль 2**

```sql
SELECT *
FROM sem12.test_table;
```

Транзакция видит свои изменения, все в порядке.

В то же время первая консоль видит только свои изменения, так как вторая транзакция еще не завершена:

**Консоль 1**

```sql
SELECT *
FROM sem12.test_table;
```

Завершим транзакцию:

**Консоль 2**

```sql
COMMIT;
```

Проверим итоговое состояние:

**Консоль 1 или консоль 2**

```sql
SELECT *
FROM sem12.test_table;
```

На уровне `READ COMMITTED` вторая транзакция после ожидания увидит актуальную версию строки и сможет применить своё изменение.

---

Сделаем то же самое на уровне REPEATABLE READ:

**Консоль 1**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

**Консоль 2**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

Прочитаем строку в обеих транзакциях

**Консоль 1**

```sql
SELECT *
FROM sem12.test_table
WHERE my_id = 1;
```

**Консоль 2**

```sql
SELECT *
FROM sem12.test_table
WHERE my_id = 1;
```

Изменим строку в первой транзакции:

**Консоль 1**

```sql
UPDATE sem12.test_table
SET my_text_field = 'rr_console_1'
WHERE my_id = 1;
```

Попробуем изменить ту же строку во второй транзакции:

**Консоль 2**

```sql
UPDATE sem12.test_table
SET my_text_field = 'rr_console_2'
WHERE my_id = 1;
```

Вторая транзакция будет ждать завершения первой.

Зафиксируем первую транзакцию:

**Консоль 1**

```sql
COMMIT;
```

Посмотрим, что произошло во второй консоли.

После разблокировки PostgreSQL обнаружит, что строка была изменена после начала второй транзакции, а её снимок данных уже устарел. Поэтому вторая транзакция завершится ошибкой вида:

```sql
ERROR: could not serialize access due to concurrent update
```

Теперь придется откатить вторую транзакцию - так как в ней была операция, завершившаяся ошибкой, сохранить транзакцию нельзя, нарушится условие атомарности.

**Консоль 2**

```sql
ROLLBACK;
```

Таким образом, на уровне `REPEATABLE READ` каждая транзакция работает с фиксированным снимком данных, поэтому после изменения строки другой транзакцией PostgreSQL не разрешает тихо «пересобрать» операцию поверх новой версии строки.

Проверим поведение `SERIAL` при вставке из двух транзакций

Начнем две транзакции.

**Консоль 1**

```sql
BEGIN;
```

**Консоль 2**

```sql
BEGIN;
```

Выполним вставку в первой транзакции.

**Консоль 1**

```sql
INSERT INTO sem12.test_table (my_text_field)
VALUES ('insert_from_console_1');

SELECT * FROM sem12.test_table;
```

Выполним вставку во второй транзакции.

**Консоль 2**

```sql
INSERT INTO sem12.test_table (my_text_field)
VALUES ('insert_from_console_2');

SELECT * FROM sem12.test_table;
```

Нужно обратить внимание на значение `my_id`.

Откатим одну из транзакций, например вторую.

**Консоль 2**

```sql
ROLLBACK;
```

Вставим еще одну строку в первой консоли:

**Консоль 1**

```sql
INSERT INTO sem12.test_table (my_text_field)

SELECT * FROM sem12.test_table;
```

Можно заметить, что идентификаторы могут идти с пропусками.  
Причина в том, что объект `SEQUENCE` не откатывается вместе с транзакцией.

Не забываем закрывать транзакции.

**Консоль 1**

```sql
COMMIT;
```

Продемонстрируем особенности работы транзакций уровня `SERIALIZABLE`.

Этот уровень подразумевает, что транзакции должны иметь возможность быть выполненными последовательно для успешного завершения. В частности, если одна транзакция меняет изначальные данные, то другая транзакция не может использовать эти данные, так как изначально имеет доступ только к снимку данных, актуальному на момент начала исполнения транзакции, который стал бы неактуальным в случае последовательного исполнения.

Для демонстрации создадим таблицу, в которой будем хранить информацию о врачах. Предположим, что по правилу предметной области в смене всегда должен оставаться хотя бы один дежурный врач.

Пусть изначально на дежурстве находится 2 врача, и каждый из них, зная что на данный момент на дежурстве есть не только он, попытается снять себя с дежурства. Наша цель - не допустить такой возможности, ведь в таком случае на дежурстве не останется никого.

Подготовим таблицу и тестовые данные.

**Консоль 1**

```sql
CREATE TABLE sem12.on_call (
    doctor_id   integer PRIMARY KEY,
    doctor_name text NOT NULL,
    on_duty     boolean NOT NULL
);

INSERT INTO sem12.on_call (doctor_id, doctor_name, on_duty)
VALUES
    (1, 'Alice', true),
    (2, 'Bob', true);

SELECT *
FROM sem12.on_call
ORDER BY doctor_id;
```

---

Проверим поведение уровня `REPEATABLE READ`

Начнем две транзакции уровня `REPEATABLE READ`.

**Консоль 1**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

**Консоль 2**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

Считаем количество дежурных врачей в первой транзакции.

**Консоль 1**

```sql
SELECT count(*) AS cnt
FROM sem12.on_call
WHERE on_duty = true;
```

Транзакция увидит, что дежурят 2 врача.

Снимем первого врача с дежурства, но пока не будем фиксировать изменения.

**Консоль 1**

```sql
UPDATE sem12.on_call
SET on_duty = false
WHERE doctor_id = 1;
```

Считаем количество дежурных врачей во второй транзакции.

**Консоль 2**

```sql
SELECT count(*) AS cnt
FROM sem12.on_call
WHERE on_duty = true;
```

Вторая транзакция тоже увидит 2 дежурных врача, потому что работает со своим снимком данных.

Снимем второго врача с дежурства.

**Консоль 2**

```sql
UPDATE sem12.on_call
SET on_duty = false
WHERE doctor_id = 2;
```

Теперь зафиксируем изменения в обеих транзакциях.

**Консоль 1**

```sql
COMMIT;
```

**Консоль 2**

```sql
COMMIT;
```

Проверим итоговое состояние таблицы.

**Консоль 1 или консоль 2**

```sql
SELECT *
FROM sem12.on_call
ORDER BY doctor_id;
```

В результате оказывается, что оба врача сняты с дежурства.  
Это показывает, что уровень `REPEATABLE READ` в PostgreSQL сохраняет согласованный снимок данных внутри транзакции, но не гарантирует полной сериализуемости параллельного выполнения, ведь если бы транзакции были выполнены последовательно, то в одной из транзакций запрос, возвращающий количество врачейц на дежурстве вернул бы значение `1`.

Проверим поведение уровня `SERIALIZABLE`

Вернем таблицу в исходное состояние.

**Консоль 1**

```sql
UPDATE sem12.on_call
SET on_duty = true;
```

Начнем две транзакции уровня `SERIALIZABLE`.

**Консоль 1**

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
```

**Консоль 2**

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
```

Считаем количество дежурных врачей в первой транзакции.

**Консоль 1**

```sql
SELECT count(*) AS cnt
FROM sem12.on_call
WHERE on_duty = true;
```

Снимем первого врача с дежурства.

**Консоль 1**

```sql
UPDATE sem12.on_call
SET on_duty = false
WHERE doctor_id = 1;
```

Считаем количество дежурных врачей во второй транзакции.

**Консоль 2**

```sql
SELECT count(*) AS cnt
FROM sem12.on_call
WHERE on_duty = true;
```

Снимем второго врача с дежурства.

**Консоль 2**

```sql
UPDATE sem12.on_call
SET on_duty = false
WHERE doctor_id = 2;
```

Попробуем зафиксировать изменения.

**Консоль 1**

```sql
COMMIT;
```

**Консоль 2**

```sql
COMMIT;
```

Одна из транзакций должна завершиться ошибкой сериализации.

Пример сообщения об ошибке:

```sql
ERROR: could not serialize access due to read/write dependencies among transactions
```

Если транзакция завершилась ошибкой, ее нужно откатить.

**Консоль, в которой возникла ошибка**

```sql
ROLLBACK;
```

Проверим итоговое состояние таблицы.

**Консоль 1 или консоль 2**

```sql
SELECT *
FROM sem12.on_call
ORDER BY doctor_id;
```

В результате хотя бы один врач останется дежурным.

Почему так произошло?

Транзакция, которая завершается второй, ввиду уровня изоляции `SERIALIZABLE` должна иметь возможность корректно выполниться "последовательно" с первой транзакцией. Но она обращалась к данным, которые в первой транзакции были изменены, а значит существует вероятность, что данные, которые были считаны второй транзакцией, оказались бы при "последовательном" выполнении неактуальными (в нашем случае так и оказалось, но даже если бы значение, которое возвращал `SELECT` во второй транзакции, не поменялось, все равно была бы возвращена ошибка сериализации)

Таким образом, на уровне `REPEATABLE READ` каждая транзакция работает со своим неизменным снимком данных, поэтому обе транзакции могут принять решение на основе одинакового исходного состояния и вместе нарушить бизнес-правило. На уровне `SERIALIZABLE` PostgreSQL отслеживает зависимости между транзакциями и не допускает такого результата: одна из транзакций будет прервана ошибкой сериализации.

Начнем транзакцию.

**Консоль 1**

```sql
BEGIN;
```

Добавим несколько строк.

**Консоль 1**

```sql

VALUES
    ('sp_value_1'),
    ('sp_value_2');

FROM sem12.test_table
ORDER BY my_id;
```

Создадим первую точку сохранения.

**Консоль 1**

```sql

```

Добавим еще несколько строк.

**Консоль 1**

```sql
INSERT INTO sem12.test_table (my_text_field)
VALUES
    ('sp_value_3'),
    ('sp_value_4');

SELECT *
FROM sem12.test_table
ORDER BY my_id;
```

Создадим вторую точку сохранения.
