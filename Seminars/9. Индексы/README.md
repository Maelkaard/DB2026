# Занятие №9: Жизненный цикл запроса, планировщик и индексы

## Жизненный цикл запроса

При выполнении SQL-запроса PostgreSQL проходит несколько этапов.

### 1. Подключение к СУБД

СУБД получает запрос в виде обычного текста.

### 2. Разбор запроса (parsing)

Парсер проверяет корректность синтаксиса и строит дерево запроса.

Дерево запроса - это специальное внутреннее представление SQL-запроса после его разбора. Оно содержит полную структурированную информацию о запросе.

В нем отражается:

- тип команды (SELECT, INSERT, UPDATE, DELETE)
- список используемых отношений (таблиц, представлений)
- целевое отношение, если запрос изменяет данные
- список полей результата (в часности `*` раскрывается в полный список столбцов)
- условия фильтрации
- структура соединений
- а также другая информация (ORDER BY, LIMIT и т.п.)

Например, запрос

```sql
SELECT *
FROM order
WHERE order_dt > '2025-12-12';
```

на уровне идеи превращается во внутреннюю структуру вида:

```text
Тип команды: SELECT
Источник данных: order
Список полей: order_id, customer_id, order_dt, ...
Условия: order_dt > '2025-12-12'
```

### 3. Переписывание запроса (rewrite)

После построения дерева запроса PostgreSQL может переписать запрос, в частности раскрыть представление в его исходный `SELECT` или превратить подзапрос в соединение. После этого строится новое дерево запроса.


### 4. Планирование (planning)

На этом этапе PostgreSQL строит несколько возможных способов выполнения запроса и оценивает их стоимость.

Планировщик выбирает способ с наименьшей ожидаемой стоимостью.

Планировщик запросов (query planner) - это компонент PostgreSQL, который выбирает способ выполнения SQL-запроса. Именно он определяет последовательность действий, которая будет выполнена при выполнении запроса - пользователь определяет только желаемый результат.

### 5. Выполнение (execution)

После выбора плана PostgreSQL передает его исполнителю, и запрос реально выполняется.

## План запроса

План запроса - это конкретный способ выполнения SQL-запроса, выбранный планировщиком.

Чтобы увидеть план, используется оператор `EXPLAIN`.

Создадим схему:

```sql
DROP SCHEMA IF EXISTS sem9 CASCADE;
CREATE SCHEMA sem9;

CREATE TABLE sem9.customer (
    customer_id   INTEGER PRIMARY KEY,
    email         TEXT NOT NULL UNIQUE,
    full_name     TEXT NOT NULL,
    city          TEXT NOT NULL,
    signup_dt     DATE NOT NULL
);

CREATE TABLE sem9.order (
    order_id        BIGINT PRIMARY KEY,
    customer_id    INTEGER NOT NULL REFERENCES sem9.customer(customer_id),
    order_dt       DATE NOT NULL,
    status         TEXT NOT NULL CHECK (status IN ('shipped', 'processing', 'returned', 'cancelled')),
    total_amount   NUMERIC(10,2) NOT NULL CHECK (total_amount >= 0),
    warehouse_id   INTEGER NOT NULL,
    payment_method TEXT NOT NULL CHECK (payment_method IN ('card', 'cash', 'transfer'))
);
```

```sql
EXPLAIN
SELECT *
FROM sem9.order
WHERE total_amount >= 10;
```

Возможный результат:

```text
Seq Scan on "order"  (cost=0.00..17.88 rows=210 width=100)
  Filter: (total_amount >= '10'::numeric)
```

План показывает:

- какие операции будут выполняться (в данном случае - только Seq Scan)
- в каком порядке они выполняются
- какую стоимость планировщик ожидает (стоимость в условных единицах)
- сколько строк он предполагает получить
- размер строки в байтах

`EXPLAIN` показывает только оценочный план, без реального выполнения запроса. Именно поэтому нет ничего необычного в том что планировщик ожидает от пустой таблицы 210 строк. Увеличения точности оценки можно добиться при помощи команды `ANALYZE` (но точность все еще не будет полной):

```sql
ANALYZE;
EXPLAIN
SELECT *
FROM sem9.order
WHERE total_amount >= 10;
```

Возможный результат:

```text
Seq Scan on "order"  (cost=0.00..0.00 rows=1 width=100)
  Filter: (total_amount >= '10'::numeric)
```

### EXPLAIN ANALYZE

Для того, чтобы выполнить запрос и получить информацию по времени выполнения, существует оператор `EXPLAIN ANALYZE`.

```sql
EXPLAIN ANALYZE
SELECT *
FROM sem9.order
WHERE total_amount >= 10;
```

Возможный результат:

```text
Seq Scan on "order"  (cost=0.00..0.00 rows=1 width=100) (actual time=0.002..0.003 rows=0 loops=1)
  Filter: (total_amount >= '10'::numeric)
Planning Time: 0.151 ms
Execution Time: 0.011 ms
```

Важно: `EXPLAIN ANALYZE` действительно запускает запрос. Для `SELECT` это просто чтение, но для `INSERT`, `UPDATE` и `DELETE` изменения будут выполнены.

### Стоимость плана

PostgreSQL сравнивает планы по стоимости (`cost`). Это не время в миллисекундах, а внутренняя условная оценка.

Обычно в плане указываются два числа:

```text
(cost=0.00..17.88)
```

- первое число - стоимость начала получения первых строк
- второе число - полная стоимость выполнения операции

Планировщик оценивает стоимость по статистике таблиц и выражений.

На оценку влияют:

- количество строк в таблицах
- распределение значений
- наличие индексов
- предполагаемая доля строк, удовлетворяющих условию

## Индексы

Индекс - это вспомогательная объект базы данных, который используется для ускорения поиска строк по значениям столбцов (или выражений).

Индексы основываются на разных структурах данных, основные - B-tree и Hash . Разные типы индексов ускоряют выполнение различных операций.

Общий синтаксис:

```sql
CREATE [UNIQUE] INDEX name ON table_name(column_name | expression) [USING method]
[WHERE expression];
```

В случае неуказания метода используется метод btree.

Вставим в таблицы данные:

```sql
INSERT INTO sem9.customer (customer_id, email, full_name, city, signup_dt)
SELECT
    g,
    'user' || g || '@example.com',
    'Customer ' || g,
    CASE g % 10
        WHEN 0 THEN 'Berlin'
        WHEN 1 THEN 'Munich'
        WHEN 2 THEN 'Hamburg'
        WHEN 3 THEN 'Cologne'
        WHEN 4 THEN 'Leipzig'
        WHEN 5 THEN 'Dresden'
        WHEN 6 THEN 'Bonn'
        WHEN 7 THEN 'Stuttgart'
        WHEN 8 THEN 'Bremen'
        ELSE 'Frankfurt'
    END,
    DATE '2020-01-01' + (g % 1800)
FROM generate_series(1, 2000) AS g;

INSERT INTO sem9.order (order_id, customer_id, order_dt, status, total_amount, warehouse_id, payment_method)
SELECT
    g,
    ((g - 1) % 2000) + 1,
    DATE '2023-01-01' + (g % 730),
    CASE
        WHEN g % 100 < 2 THEN 'cancelled'
        WHEN g % 100 < 12 THEN 'returned'
        WHEN g % 100 < 37 THEN 'processing'
        ELSE 'shipped'
    END,
    ((g % 5000) / 10.0 + 10)::NUMERIC(10,2),
    (g % 20) + 1,
    CASE g % 3
        WHEN 0 THEN 'card'
        WHEN 1 THEN 'cash'
        ELSE 'transfer'
    END
FROM generate_series(1, 30000) AS g;
```

Выполним

```sql
EXPLAIN ANALYZE
SELECT *
FROM sem9.customer
WHERE signup_dt > '2024-12-12'
```

Пример результата:
```text
Seq Scan on customer  (cost=0.00..46.00 rows=1 width=48) (actual time=0.108..0.109 rows=0 loops=1)
  Filter: (signup_dt > '2024-12-12'::date)
  Rows Removed by Filter: 2000
Planning Time: 0.074 ms
Execution Time: 0.117 ms
```

Теперь создадим индекс:

```sql
CREATE INDEX idx_customer_signup_dt ON sem9.customer(signup_dt); --тип по умолчанию - B-tree
```

Теперь снова выполним тот же запрос, и получим уже примерно следующее:

```text
Index Scan using idx_customer_signup_dt on customer  (cost=0.28..7.24 rows=1 width=48) (actual time=0.004..0.005 rows=0 loops=1)
  Index Cond: (signup_dt > '2024-12-12'::date)
Planning Time: 0.163 ms
Execution Time: 0.014 ms
```

Наблюдаем не только изменение операции (Index Scan вместо Seq Scan), но и улучшение времени работы.

При этом, выполнив

```sql
EXPLAIN ANALYZE
SELECT *
FROM sem9.customer
WHERE signup_dt > '2020-12-12'
```
снова получим Seq Scan. Это произойдет потому, что индекс ускоряет чтение данных только при высокой селективности условия (т.е. если условие отсеивает большую часть значений). Иначе планировщик оценивает Seq Scan как более эффективный.

При своей возможности ускорить выполнение запросов, индекс замедляет операции вставки и удаления данных из таблицы, т.к. полностью перестраивается при изменении данных в таблице. Таким образом стоит создавать индексы только в случае необходимости.

Индекс типа B-tree может ускорить любые операции сравнения. Индекс тип Hash лучше ускоряет операции `=` и `!=`, но ускоряет только их.

Важно - индекс ускоряет данные операции только с чистым значением столбца (или выражения), созданный выше индекс не будет применен при запросах наподобие

```sql
EXPLAIN ANALYZE
SELECT *
FROM sem9.customer
WHERE EXTRACT(year from signup_dt) > 2025
```

Можно создать индекс по нескольким столбцам, тогда он будет применяться при сравнениях например пар значений, а также при сравнениях лидирующих атрибутов. Например индекс

```sql
CREATE INDEX idx_order_customer_id_order_dt ON sem9.order(customer_id, order_dt)
```

сможет использоваться при сравнении пар значений `(customer_id, order_dt)`, а также при сравнении только `customer_id`, но не сможет использоваться при сравнении `order_dt`.

### Уникальные индексы

Уникальные индексы создаются автоматически для всех групп столбцов, обладающих ограничениями PRIMARY KEY и UNIQUE, но могут быть созданы отдельно через CREATE UNIQUE INDEX. Защищают данные от дублирования, при вставке или изменении, приводящих к появлению дубликата, вызывают ошибку

### Частичные индексы

Частичный индекс - индекс, построенный только для тех строк таблицы, которые удовлетворяют условию. Для объявления частичного индекса используется выражение WHERE при создании индекса:

```sql
CREATE INDEX idx_processing_orders ON sem9.order(customer_id)
WHERE status = 'processing'
```

Таким образом был создан индекс, который подразумевает использование только при поиске опеределенных строк таблицы (в нашем случае - обрабатываемых заказов), и не замедляет вставку и удаление других строк таблицы.

## Операции считывания данных

Основной операцией, выполняемой при выполнении запросов, является считывание данных из таблиц. Существуют различные ее виды, применимые в различных случаях.

### Sequential Scan

Sequential Scan (Seq Scan) - последовательное чтение всей таблицы.Именно он использовался в ранее рассмотренных планах запросов.

Такой способ используется, если:

- таблица маленькая
- нужно прочитать значительную часть строк (условие фильтрации обладает низкой селективностью или отсутствует)

### Index Scan

Index Scan - чтение строк через индекс.

Используется, если:

- таблица достаточно большая _(но не сильно)_
- условие обладает высокой селективностью

### Index Only Scan

Index Only Scan - чтение только из индекса, без обращения к самой таблице.

Применяется в тех же условиях, что и Index Scan, но если все нужные столбцы уже есть в индексе

### Bitmap Index Scan и Bitmap Heap Scan

Наиболее частый способ чтения в случае работы с большими данными. Требует наличия индекса. Разбивается на 2 этапа - Bitmap Index Scan и Bitmap Heap Scan.

Большие объемы данных в памяти хранятся на отдельных _страницах данных_. Операция обращения к странице является крайне дорогой, поэтому выгодно сразу определить, на каких страницах находятся инетересующие нас данные. Для этого при помощи индекса строится bitmap, т.е. буквально для каждой страницы - требуется она или нет. После этого обходятся только нужные страницы данных.

```sql
EXPLAIN ANALYZE
SELECT *
FROM sem9.customer
WHERE signup_dt > '2023-12-12'
```

Возможный план:

```text
Bitmap Heap Scan on customer  (cost=11.05..36.53 rows=358 width=48) (actual time=0.055..0.076 rows=358 loops=1)
  Recheck Cond: (signup_dt > '2023-12-12'::date)
  Heap Blocks: exact=5
  ->  Bitmap Index Scan on idx_customer_signup_dt  (cost=0.00..10.96 rows=358 width=0) (actual time=0.048..0.048 rows=358 loops=1)
        Index Cond: (signup_dt > '2023-12-12'::date)
Planning Time: 0.060 ms
Execution Time: 0.122 ms
```

## Методы соединения таблиц

При соединении таблиц PostgreSQL также выбирает конкретный алгоритм.

### Nested Loop

Nested Loop - самый простой алгоритм, подразумевающий для каждой строки левой таблицы совершение полного прохода правой таблицы с поиском совпадений по условию. Является самым медленным, но единственный позволяет использовать условия соединения не по равенству.

### Hash Join

Hash Join - более быстрый способ в случае соединения по равенству. Для всех значений атрибута соединения в меньшей таблице находится их хэш, далее для каждой строки большей таблицы ищется строка с совпадающим хэшом атрибута соединения.


### Merge Join

Merge Join - способ, подразумевающий соединение по условию равенства двух отсортированных наборов строк. Используется чаще всего при наличии в обеих таблицах индекса B-tree, в котором порядок поддерживается при построении. Является наиболее быстрым способом, поэтому часто разумно создавать индексы типа B-tree на внешние ключи для более быстрого соединения по ним.

## Практические задания

Скрипт создания схемы и заполнения данными находится в папке семинара.

Используется схема `sem9` со следующими таблицами:

`sem9.customer`

- `customer_id` - уникальный идентификатор покупателя (`PRIMARY KEY`)
- `full_name` - имя покупателя
- `city` - город
- `registration_dt` - дата регистрации
- `email` - электронная почта (`UNIQUE`)

`sem9.category`

- `category_id` - уникальный идентификатор категории (`PRIMARY KEY`)
- `category_name` - название категории

`sem9.product`

- `product_id` - уникальный идентификатор товара (`PRIMARY KEY`)
- `product_name` - название товара
- `category_id` - ссылка на категорию (`FOREIGN KEY -> category.category_id`)
- `price` - цена
- `stock_qty` - остаток на складе
- `is_active` - признак активности товара

`sem9.order`

- `order_id` - уникальный идентификатор заказа (`PRIMARY KEY`)
- `customer_id` - ссылка на покупателя (`FOREIGN KEY -> customer.customer_id`)
- `order_dt` - дата заказа
- `status` - статус заказа
- `total_amount` - итоговая сумма заказа

`sem9.order_item`

- `order_item_id` - уникальный идентификатор позиции заказа (`PRIMARY KEY`)
- `order_id` - ссылка на заказ (`FOREIGN KEY -> order_head.order_id`)
- `product_id` - ссылка на товар (`FOREIGN KEY -> product.product_id`)
- `quantity` - количество единиц товара
- `unit_price` - цена товара на момент покупки
